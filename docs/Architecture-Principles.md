# 架构原则 (Architecture Principles)

> 本文件是所有技术决策的北极星。代码可以重构, 模块可以替换, 但这些原则不可违背。
> 半年后当你忘了最初的设计, 或者新贡献者加入时, 先读这一页。
> 协同设计: 用户 (SunJialei) + Codex + GPT
> 设计文档: docs/specs/2026-07-14-desktop-pet-design.md
> 实施计划: docs/plans/2026-07-14-implementation-plan.md

---

## 1. LLM 负责表达, 不负责维护世界状态

LLM 是演员, 不是导演, 不是数据库。

导演 (Behavior Planner) 决定行为方向; SQLite 决定什么被记住; LLM 只负责把已决定的行为用自然语言表达出来。状态变更永远通过 Rust 代码完成 (Reducer / DB 操作), 永远不通过 LLM 直接写数据库。

违背此原则的信号: 让 LLM 输出 SQL, 让 LLM 直接修改 Emotion 值, 让 LLM 决定什么该存什么不该存 (那是 Memory Gate 的职责)。

## 2. BrainState 是唯一真实状态

所有 Mind 层模块读写 BrainState 快照, 不互相传参, 不各自持有状态副本。

如果两个模块需要交互, 它们通过 BrainState 间接通信: 一个写, 另一个读。不直接调用对方的方法。这让模块边界清晰, 增删模块不会引发连锁修改。

违背此原则的信号: Planner 的参数列表超过 3 个, 某个模块缓存了自己的状态副本且不同步。

## 3. Memory 可以遗忘, 但不能编造

Grounded Generation: LLM 只能引用已检索到的记忆。记忆中没有的, 说"不确定", 不编造。

遗忘是人性 (Memory Lifecycle 做的); 编造是 Bug。用户原谅"你忘了", 但不会原谅"你瞎说"。

违背此原则的信号: LLM 输出提到了检索结果中没有的事实; Fact 置信度很低但 LLM 表现得像确信无疑。

## 4. 对话管道用直接调用; 跨模块状态变化用事件广播

Gate -> Extractor -> Store -> Trigger -> Retrieval -> Planner -> Budget -> LLM 是同步顺序链, 直接调用。不用事件总线, 因为顺序流用事件会增加延迟、降低可调试性。

感知更新、情绪变化、Pending 到期这类"一个变化, 多个消费者关心"的场景, 用观察者广播。

违背此原则的信号: 对话管道里某一步变成异步事件且无法保证顺序; 两个模块为了一个事件争抢执行顺序。

## 5. Mind-Body 解耦: Body 永远活着

Body (动画、物理、昼夜、空间) 以 60fps 持续运行, 不依赖 Mind, 不依赖 LLM。

断网了, API 超时了, 数据库锁了——她照样呼吸、眨眼、打哈欠。这是"她一直活着"和"她只在聊天时活着"的根本区别。

违背此原则的信号: Body 的渲染帧率受 LLM 响应时间影响; 动画暂停等待数据库查询。

## 6. 任何新增能力都必须能关闭, 且关闭后不影响主流程

每个功能模块都有开关 (app_config 表或对话指令)。关掉系统感知, 对话照常; 关掉 Reflection, 记忆照常; 关掉主动冒泡, 她安静待着但不崩溃。

这保证了系统退化是优雅的——关掉的模块越多, 她越安静, 但永远不坏。

违背此原则的信号: 关掉某个模块后其他模块报错; 某个功能没有开关, 用户无法关闭。

## 7. 用户永远看不到系统

没有设置面板, 没有错误弹窗, 没有加载进度条 (除了模型下载, 且用角色化文案包装)。

配置通过对话完成 ("晚上 11 点后别打扰我")。错误通过角色化反应处理 (API 断了 -> "我刚刚有点走神")。连 Debug Panel 都是开发者专属, 发布版完全隐藏。

违背此原则的信号: 出现任何面向用户的系统术语 (配置、数据库、API、缓存); 用户需要点击"确定"关闭弹窗。

## 8. 成本是设计约束, 不是事后优化

系统运行在用户自配的、可能很便宜的模型上。每个 LLM 调用都要问: 这个调用真的必要吗?

Memory Gate 用最便宜的模型。Reflection 每天最多一次。不是每轮对话都需要检索。能用规则解决的不用 LLM。

违背此原则的信号: 单轮对话发起超过 2 次 LLM 调用; 某个功能在没有用户交互时持续消耗 token。

## 9. 分层复杂度: 每层刚好够用

不要一开始就做终局设计。先留扩展点, 等复杂度"长"出来。

Reflection MVP: confidence 阈值。V2: 冲突检测。V3: 正式 Validator。V4: 人工审核。
Retrieval MVP: dense 向量。V2: 混合检索。V3: 重排序。
Persona MVP: 空, 通过 Reflection 逐步建立。V2: Adaptive Traits。V3: 正式审批流。

Make the change easy, then make the easy change. (Martin Fowler)

违背此原则的信号: MVP 阶段的某个模块代码量超过其他模块的总和; 一个简单需求引入了完整的框架。

## 10. 优先增加生命感, 不优先增加功能

用户要的是陪伴, 不是工具集。

在她学会"预测你的习惯"之前, 先让她"在你难过时安静坐下"。在她学会"帮你管理日程"之前, 先让她"在你回来时说一句你回来了"。

功能的优先级排序永远是: 先让她活着 (Body), 再让她记住你 (Memory), 再让她懂你 (Persona/Soul), 最后才考虑任何工具性能力。

违背此原则的信号: 讨论新功能时先想到"有用"而不是"有趣"; 加入日历、提醒、搜索等功能性工具。

## 11. 任何模块都必须支持 Explainability

状态变化记录原因 (Change Log)。检索结果带 score breakdown + reason。Emotion 变化可追溯。Persona 更新有 Reflection 来源。

不是为了用户, 是为了开发者。当她说了一句奇怪的话, 你必须能在 Debug Panel 里看到完整的决策链: 输入 -> Gate 判断 -> 检索了什么 -> Planner 选了什么 Intent -> LLM 拿到了什么 Prompt。

违背此原则的信号: 某个行为无法解释为什么发生; Debug Panel 有空白区域。

## 12. 沉默也是表达

不是每个输入都需要回复。不是每个回复都需要文字。

有时候她只是走过来坐下。有时候气泡里只有一个省略号。有时候什么都不做, 只是呼吸。

Behavior Planner 的 Intent 输出必须支持 "silence" 作为有效行为, 和 "speak" 同等地位。

违背此原则的信号: 每次用户输入都触发 LLM 调用; 回复总是充满文字, 从不沉默。
